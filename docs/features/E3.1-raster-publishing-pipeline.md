# E3-1: Raster Publishing Pipeline

**Decision record:** `docs/architecture/adr/ADR-012-raster-publishing-pipeline.md`

This is the operator runbook for publishing a GeoTIFF (historical map, plan, or the future DEM) so it's reachable by the frontend, plus how to reach GeoServer's admin UI from a machine other than the NAS itself — e.g. your laptop, when your QGIS work and source GeoTIFFs live on your desktop.

---

## Architecture, in one picture

```
Browser (rinsewillet.net/webGIS/...)
      │
      ▼
ancientdata backend (public, on webgis-edge)
      │  GET /api/raster/**  (WMS/WMTS/GWC only — /rest/**, /web/** blocked)
      ▼
geoserver container (internal-only, webgis-edge network)
      │  reads
      ├─▶ /volume1/docker/ancientdata/geoserver   (data_dir bind mount — workspace/store/style config, GWC cache)
      └─▶ /volume1/docker/ancientdata/rastermaps  (separate bind mount, read-only — raw source GeoTIFFs)
```

Source rasters live in their own top-level NAS directory, `/volume1/docker/ancientdata/rastermaps`, deliberately separate from GeoServer's own `data_dir`. `data_dir` holds GeoServer's *operational* state — most notably the GWC tile cache, which is large and fully regenerable, so backing it up is wasted space. `rastermaps` holds only the immutable source-of-truth files, so it can be pointed at by a NAS backup job on its own (see "Backup" below). It's mounted at `/opt/geoserver/data_dir/rastermaps` inside the container (nested from GeoServer's point of view, so its store-creation file browser can reach it) while staying a fully independent directory on the NAS host (so backup jobs can target it precisely).

GeoServer's admin UI and REST API are **not** proxied publicly and keep their current LAN/WARP-only access (see next section). Only OGC tile/map-rendering traffic goes through `ancientdata`.

## Accessing GeoServer admin from another computer (e.g. your laptop)

Your QGIS work and source GeoTIFFs live on your desktop; this section is for reaching GeoServer's admin UI (to create a store/layer, upload a style, configure GWC) from **any other machine**, including this laptop.

### On the home LAN

Browse directly to:

```
http://192.168.1.50:2675/geoserver
```

(same NAS LAN IP / port already used for QGIS's PostGIS connection — see `AncientDataWebGIS/README.md` and `ancientdataworkspace/deploy/README.md` §8). Login is `admin` / the value of `GEOSERVER_ADMIN_PASSWORD` in the NAS's `.env`.

### Away from home (this laptop, or anywhere else)

Reuse the **Cloudflare WARP** setup already configured for remote database access (E7 / `ADR-010`) — no new infrastructure needed:

1. Install the Cloudflare WARP client, log into the project's Zero Trust team (same one used for `DB_URL` remote access).
2. Once WARP is connected, `192.168.1.50:2675` becomes reachable transparently, exactly as on the home LAN.
3. Browse to `http://192.168.1.50:2675/geoserver` as above.

If WARP isn't set up on this machine yet, full walkthrough: `ancientdataworkspace/deploy/README.md` §8, and `docs/architecture/adr/ADR-010-remote-offline-dev-environment.md`.

> This is admin-only access for you (or an ADMIN-authenticated operator) — it is unrelated to how the public frontend reaches raster tiles, which goes through the `ancientdata` backend proxy instead (see architecture diagram above).

## Publishing a new raster (manual steps, per raster)

These are GeoServer admin/GDAL steps — not application code. Repeat per historical map/plan. The DEM specifically has extra sizing/overview considerations tracked separately in **E3-4**.

1. **(Recommended, required for large rasters like the DEM) Convert to Cloud-Optimized GeoTIFF (COG)** before publishing, so GeoServer only reads the tiles/overview level a given request actually needs instead of the whole file:
   ```bash
   gdal_translate input.tif output_cog.tif -of COG -co COMPRESS=DEFLATE
   ```
   (If starting from a plain GeoTIFF you'd rather not fully reconvert, `gdaladdo` alone will at least add overviews.) Detailed DEM-specific conversion steps are E3-4's scope — flag it there when we get to that story.
2. Copy the (converted) GeoTIFF onto the NAS, under `/volume1/docker/ancientdata/rastermaps/<category>/<collection>/`, e.g. `/volume1/docker/ancientdata/rastermaps/historical-maps/1818-de-man/`.
3. In the GeoServer admin UI (see access instructions above): create/select a workspace → add a new **Store** (GeoTIFF) → browse to the file under `rastermaps/<category>/<collection>/...` (visible inside the container at `/opt/geoserver/data_dir/rastermaps/...`) → publish it as a **Layer** → set its style (SLD) if not the default greyscale/rainbow ramp.
4. Enable **tile caching** for the layer (GeoServer's built-in GWC — "Tile Caching" tab on the layer, or the separate "Caching Defaults" admin page) so repeat requests at the same zoom/tile don't re-render.
5. Verify it's reachable through the backend proxy (replace `<workspace>`/`<layer>` and adjust for your dev/prod host):
   ```
   http://localhost:8080/api/raster/<workspace>/wms?service=WMS&version=1.1.0&request=GetMap&layers=<workspace>:<layer>&bbox=...&width=256&height=256&srs=EPSG:4326&format=image/png
   ```
   A `403` means the path matched the admin denylist (check for a stray `/rest/`/`/web/` in the URL); a `502` means GeoServer itself isn't reachable from the `ancientdata` container.
6. **Known follow-up (not yet done):** GeoServer's `GetCapabilities` documents will self-reference GeoServer's *internal* address until its proxy base URL setting is pointed at the public `/api/raster` path. Needed before capabilities documents are handed directly to any external client (E3-2's catalog endpoint sidesteps this by describing layers itself rather than forwarding GetCapabilities, but flag this if that changes).

Wiring specific layers into `layersConfig.ts`/the catalog endpoint is **E3-2**/**E3-3**, not this story.

## DEM-specific conversion (E3-4)

The general recipe above (step 1) uses a plain `gdal_translate ... -of COG -co COMPRESS=DEFLATE` example. For the ~80GB DEM, two of its defaults are wrong for continuous elevation data and need to be made explicit.

**Before converting, always check the actual source file first:**

```bash
gdalinfo dem_source.tif
```

Confirm native pixel size (ground sample distance) and vertical units — `gdalinfo <file>.tif | grep -E "Pixel Size|Coordinate System"` gives the exact figure directly, don't estimate it from geography. **Measured on the actual `research_area_Gelderland_NRW_cog.tif`: Pixel Size ≈ 1.0001m** (confirmed via `gdalinfo`, not the ~0.5m originally assumed here before real data existed to check against) — adjust the zoom range and overview level list per-file if a different DEM reports something else.

**Target zoom range: 8–17** (revised down from an initial 8–18 estimate once real pixel-size data was available — see below). Wider than the 12–19 used for the historical map sheets, and asymmetric — lower at the small-scale end, similar at the large-scale end. This DEM covers a large area (roughly Utrecht/Gelderland, NL, up to Duisburg, DE) and needs to serve two very different use cases:
- **z8–z10 (regional):** large geomorphological features — the Veluwe and Reichswald moraine massifs, the Rhine river valley — visible even from a heavily downsampled overview.
- **z15–z17 (near-native detail):** archaeological microrelief — Roman road embankments, tumuli, Celtic field lynchets (e.g. near Kleve) — which are subtle (often sub-meter) relief features only visible close to the source resolution. At this region's latitude (~51.7°N), z17 ≈ 0.74m/px (slightly finer than the measured ~1.0m native resolution — normal, mild interpolation) while z18 ≈ 0.37m/px (nearly 3x finer than native — pure upsampling with no real added detail, and wasted GWC cache/render cost for tiles that just look like blown-up duplicates of z17). There is little reason to publish beyond a DEM's native resolution's effective zoom level. **Check this per file** (`gdalinfo | grep "Pixel Size"`) rather than assuming every DEM shares this figure — a genuinely ~0.5m-class source would earn z18 back.

**Conversion command:**

```bash
gdal_translate dem_source.tif dem_source_cog.tif \
  -of COG \
  -co COMPRESS=DEFLATE \
  -co RESAMPLING=AVERAGE \
  -co OVERVIEW_RESAMPLING=AVERAGE \
  -co BIGTIFF=YES
```

- **`RESAMPLING=AVERAGE`/`OVERVIEW_RESAMPLING=AVERAGE`** — the historical-map pipeline didn't need to specify this (nearest-neighbor default is fine for a scanned RGB sheet). For elevation data it's wrong: nearest-neighbor overview building picks one arbitrary source pixel's value per aggregated output pixel, which at these zoom-out ratios can either erase a subtle embankment entirely or, worse, alias it into a false spike/pit that isn't in the source data. `average` preserves the mean elevation trend at each overview level instead.
- **`COMPRESS=DEFLATE`** is the safe lossless default, same as the historical-map pipeline. If the resulting COG is still uncomfortably large for the NAS's 4GB-RAM serving budget, `-co COMPRESS=LERC_ZSTD -co MAX_Z_ERROR=0.02` (GDAL ≥3.x) is worth testing instead — LERC bounds the introduced elevation error (here, ±2cm), which is typically well inside the vertical noise floor of LiDAR-derived DEM data anyway, and compresses continuous elevation surfaces substantially better than DEFLATE. Treat this as an optional, reversible experiment (re-run from the untouched source `.tif` if the error tolerance turns out to matter) rather than the default — confirm actual size savings against the real 80GB file before committing to it.

**Confirm the overview pyramid was built as expected:**

```bash
gdalinfo dem_source_cog.tif | grep -A2 Overview
```

Steps 2–6 of the general recipe above (copy to `rastermaps/`, create the GeoServer store/layer, enable GWC tile caching, verify via a `GetMap` WMS request through `/api/raster/<workspace>/wms`) are unchanged — this section only replaces step 1's conversion command for this specific file.

**Elevation visualization (E3-5 — decided):** a flat/default elevation color ramp alone doesn't make the research-relevant features (embankments, Celtic field lynchets, tumuli — often tens of centimeters of relief over tens of meters) visible. The chosen approach, once real DEM tiles existed to design against:

1. **Colour ramp** — `dem-elevation-ramp.sld` (this directory) is one shared style applied to every elevation DEM layer in GeoServer, spanning -25m to 155m (the combined measured range across all five published DEMs, see the SLD's own header comment for the per-layer numbers). Shared rather than per-layer-normalized, so the same colour reads as the same elevation everywhere you pan — supports the regional geomorphology reading (Veluwe/Reichswald moraine highs vs. the Rhine/Maas valley lowlands) at small-to-mid zoom.
2. **Hillshade** — GeoServer's own SLD `ShadedRelief` only supports a single light azimuth, which can hide a linear feature (an embankment, a lynchet) that happens to run parallel to that light direction. Instead, each elevation DEM gets a **multidirectional hillshade sibling**, generated separately:
   ```bash
   gdaldem hillshade <dem>_cog.tif <dem>_hillshade_cog.tif -multidirectional -of COG -co COMPRESS=DEFLATE
   ```
   Published as its own GeoServer store/layer (default greyscale style, no custom SLD needed) and its own `RasterLayerDTO` catalog entry with `hillshade = true`, listed immediately before its elevation counterpart so it defaults to a higher z-index. The frontend renders it with a `mix-blend-mode: multiply` CSS class (`.physical-layer--hillshade`, `MapContent.css`) instead of as an opaque tile, so it darkens/textures the colour-ramped elevation beneath it — both stay independently toggleable/opacity-adjustable via the existing Physical group controls, rather than being baked into one fixed server-side composite.

**Performance note (per ADR-012 "When to Revisit"):** if COG+GWC serving of this DEM (z8–17, ~80GB source) performs unacceptably on the NAS's 4GB RAM even with the overview pyramid above, fall back to Option B (pre-tiled static XYZ pyramid) for this layer specifically, while historical maps stay on COG+GWC.

**Catalog entry:** once the DEM is actually published as a GeoServer layer, add its entry to `RasterCatalogService` the same way the two De Man sheets were added in E3-2 — read the real WGS84 bounds off GeoServer's layer "Publishing" tab, set `category = RasterLayerCategory.DEM` (not `HISTORICAL_MAP`), and set `zoom` to whatever range was actually confirmed/published for that specific file via its measured `Pixel Size` (starting point: 8–17, see above — check per file, don't copy-paste blindly). This is a small, mechanical addition, not a new story.

**Multiple DEM source files (not one 80GB monolith):** in practice the DEM data exists as several separate, non-overlapping local files surrounding one large (~31GB) regional file, rather than a single combined source. Each gets published independently — its own COG conversion, own GeoServer store/layer, own `rastermaps/dem/<collection>/` subdirectory, own `RasterLayerDTO` catalog entry — exactly the same "one file = one layer = one catalog entry" pattern already used for the two De Man historical map sheets. All DEM entries share the same zoom convention (8–17, per the measured pixel size above) for consistency, even where a smaller local file's low end (z8–10) is visually uninteresting for its modest extent — this keeps the DEM category behaving as one predictable group in the `LayerPanel` rather than each entry having its own floor/ceiling, unless a specific file's own measured resolution justifies a different ceiling. If two DEM source files are later found to overlap, that needs a specific decision (which one wins, or a GeoServer `ImageMosaic`) before publishing both — don't publish overlapping DEM layers as independent entries without resolving that first.

## Backup

Per `ADR-012`, source GeoTIFFs are backed up at the **NAS level**, not by the application (unlike user-uploaded media, which `NasBackupService`/`ADR-006` already covers end-to-end in-app).

**Manual action needed:** point your NAS backup job (e.g. Synology HyperBackup) at `/volume1/docker/ancientdata/rastermaps` — the dedicated source-raster directory (see architecture diagram above), not `/volume1/docker/ancientdata/geoserver` (GeoServer's own data_dir, whose bulk is the regenerable GWC tile cache, not worth backing up). `ADR-001` documents HyperBackup covering `/volume1/docker/postgis_pgadmin_stack/` — a different parent path — so `rastermaps` is not automatically covered by that and needs its own addition.
