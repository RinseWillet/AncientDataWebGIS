# E3-1: Raster Publishing Pipeline

**Decision record:** `docs/architecture/adr/ADR-012-raster-publishing-pipeline.md`

This is the operator runbook for publishing a GeoTIFF (historical map, plan, or the future DEM) so it's reachable by the frontend, plus how to reach GeoServer's admin UI from a machine other than the NAS itself — e.g. your laptop, when your QGIS work and source GeoTIFFs live on your desktop.

---

## Architecture, in one picture

```
Browser (rinsewillet.net/webGIS/...)
      │
      ▼
ancientdata backend (public, on webgis-edge)
      │  GET /api/raster/**  (WMS/WMTS/GWC only — /rest/**, /web/** blocked)
      ▼
geoserver container (internal-only, webgis-edge network)
      │  reads
      ├─▶ /volume1/docker/ancientdata/geoserver   (data_dir bind mount — workspace/store/style config, GWC cache)
      └─▶ /volume1/docker/ancientdata/rastermaps  (separate bind mount, read-only — raw source GeoTIFFs)
```

Source rasters live in their own top-level NAS directory, `/volume1/docker/ancientdata/rastermaps`, deliberately separate from GeoServer's own `data_dir`. `data_dir` holds GeoServer's *operational* state — most notably the GWC tile cache, which is large and fully regenerable, so backing it up is wasted space. `rastermaps` holds only the immutable source-of-truth files, so it can be pointed at by a NAS backup job on its own (see "Backup" below). It's mounted at `/opt/geoserver/data_dir/rastermaps` inside the container (nested from GeoServer's point of view, so its store-creation file browser can reach it) while staying a fully independent directory on the NAS host (so backup jobs can target it precisely).

GeoServer's admin UI and REST API are **not** proxied publicly and keep their current LAN/WARP-only access (see next section). Only OGC tile/map-rendering traffic goes through `ancientdata`.

---

## Accessing GeoServer admin from another computer (e.g. your laptop)

Your QGIS work and source GeoTIFFs live on your desktop; this section is for reaching GeoServer's admin UI (to create a store/layer, upload a style, configure GWC) from **any other machine**, including this laptop.

### On the home LAN

Browse directly to:

```
http://192.168.1.50:2675/geoserver
```

(same NAS LAN IP / port already used for QGIS's PostGIS connection — see `AncientDataWebGIS/README.md` and `ancientdataworkspace/deploy/README.md` §8). Login is `admin` / the value of `GEOSERVER_ADMIN_PASSWORD` in the NAS's `.env`.

### Away from home (this laptop, or anywhere else)

Reuse the **Cloudflare WARP** setup already configured for remote database access (E7 / `ADR-010`) — no new infrastructure needed:

1. Install the Cloudflare WARP client, log into the project's Zero Trust team (same one used for `DB_URL` remote access).
2. Once WARP is connected, `192.168.1.50:2675` becomes reachable transparently, exactly as on the home LAN.
3. Browse to `http://192.168.1.50:2675/geoserver` as above.

If WARP isn't set up on this machine yet, full walkthrough: `ancientdataworkspace/deploy/README.md` §8, and `docs/architecture/adr/ADR-010-remote-offline-dev-environment.md`.

> This is admin-only access for you (or an ADMIN-authenticated operator) — it is unrelated to how the public frontend reaches raster tiles, which goes through the `ancientdata` backend proxy instead (see architecture diagram above).

## Publishing a new raster (manual steps, per raster)

These are GeoServer admin/GDAL steps — not application code. Repeat per historical map/plan. The DEM specifically has extra sizing/overview considerations tracked separately in **E3-4**.

1. **(Recommended, required for large rasters like the DEM) Convert to Cloud-Optimized GeoTIFF (COG)** before publishing, so GeoServer only reads the tiles/overview level a given request actually needs instead of the whole file:
   ```bash
   gdal_translate input.tif output_cog.tif -of COG -co COMPRESS=DEFLATE
   ```
   (If starting from a plain GeoTIFF you'd rather not fully reconvert, `gdaladdo` alone will at least add overviews.) Detailed DEM-specific conversion steps are E3-4's scope — flag it there when we get to that story.
2. Copy the (converted) GeoTIFF onto the NAS, under `/volume1/docker/ancientdata/rastermaps/<category>/<collection>/`, e.g. `/volume1/docker/ancientdata/rastermaps/historical-maps/1818-de-man/`.
3. In the GeoServer admin UI (see access instructions above): create/select a workspace → add a new **Store** (GeoTIFF) → browse to the file under `rastermaps/<category>/<collection>/...` (visible inside the container at `/opt/geoserver/data_dir/rastermaps/...`) → publish it as a **Layer** → set its style (SLD) if not the default greyscale/rainbow ramp.
4. Enable **tile caching** for the layer (GeoServer's built-in GWC — "Tile Caching" tab on the layer, or the separate "Caching Defaults" admin page) so repeat requests at the same zoom/tile don't re-render.
5. Verify it's reachable through the backend proxy (replace `<workspace>`/`<layer>` and adjust for your dev/prod host):
   ```
   http://localhost:8080/api/raster/<workspace>/wms?service=WMS&version=1.1.0&request=GetMap&layers=<workspace>:<layer>&bbox=...&width=256&height=256&srs=EPSG:4326&format=image/png
   ```
   A `403` means the path matched the admin denylist (check for a stray `/rest/`/`/web/` in the URL); a `502` means GeoServer itself isn't reachable from the `ancientdata` container.
6. **Known follow-up (not yet done):** GeoServer's `GetCapabilities` documents will self-reference GeoServer's *internal* address until its proxy base URL setting is pointed at the public `/api/raster` path. Needed before capabilities documents are handed directly to any external client (E3-2's catalog endpoint sidesteps this by describing layers itself rather than forwarding GetCapabilities, but flag this if that changes).

Wiring specific layers into `layersConfig.ts`/the catalog endpoint is **E3-2**/**E3-3**, not this story.

## Backup

Per `ADR-012`, source GeoTIFFs are backed up at the **NAS level**, not by the application (unlike user-uploaded media, which `NasBackupService`/`ADR-006` already covers end-to-end in-app).

**Manual action needed:** point your NAS backup job (e.g. Synology HyperBackup) at `/volume1/docker/ancientdata/rastermaps` — the dedicated source-raster directory (see architecture diagram above), not `/volume1/docker/ancientdata/geoserver` (GeoServer's own data_dir, whose bulk is the regenerable GWC tile cache, not worth backing up). `ADR-001` documents HyperBackup covering `/volume1/docker/postgis_pgadmin_stack/` — a different parent path — so `rastermaps` is not automatically covered by that and needs its own addition.
